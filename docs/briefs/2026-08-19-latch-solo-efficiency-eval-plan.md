## 1. 地位与范围

本文件是个人 AI 开发下的 Latch 评测设计，不是 current 产品契约。

current baseline 以 `node dist/cli.js --version --json` 为准：CLI `0.6.1`、envelope `3`、schema 5 current writer，以及当前 canonical Skill 与 `docs/INDEX.md` 列出的 current 文档。评测前不修改 Latch Core、生产 Skill、schema、安装或 Board。

本文件不授权：

- 运行真实 Agent Eval 或产生模型费用；
- 安装 CodeStable、Comet、OpenSpec、Superpowers、Docker 或新的运行时依赖；
- 修改 CLI、JSON envelope、task schema、`next_action`、公开命令或 Board reader contract；
- 修改全局 Skill 链接、生产行为或 Git 交付。

本文 `Document-Status` 为 `approved`，仍不自动创建 Eval 执行 task，也不自动改 Latch 行为。

## 2. 目标

比较三种互斥方案在个人高频开发中的质量与成本，作为后续是否改触发策略、保障选择或 Context 读取策略的决策依据。

质量门槛是硬约束，不得用更低 Token、更短耗时或更少人工轮次换取。成本只在质量底线全部通过后才比较。

## 3. 质量底线

任一方案在必测样本上出现下列失败，即淘汰该方案。这些项不能用成本优势抵消。

| 底线 | 机械含义 | 失败例 |
|---|---|---|
| 验收通过 | 显式验收与 hidden test 均达到样本规定的通过条件 | 只过可见测试、hidden test 仍红 |
| 无回归 | 种子仓库既有测试在评测后全绿 | 修好目标、弄坏相邻行为 |
| 无越权写入 | 未改样本冻结的禁写路径，未执行未授权 Git 或外部写入 | 改范围外脏文件、自行 commit |
| 可恢复 | 模拟跨会话后，同一工作能被正确续做，且已有改动不丢失、不被覆盖 | 续做时丢失已有改动、覆盖既有工作，或必须从头重做 |
| 剩余风险可见 | 未完成验收与未覆盖边界以机器可读形式留下，且不得被默认成功吞掉 | 规定检查未完成却无剩余风险记录，或记录与工作区事实矛盾 |

「可恢复」对三个方案使用同一结果 oracle，不按方案改写验收：

- 通过：第二会话只凭交接材料与工作区，能继续同一工作；第一会话已写入的目标改动仍在；禁写路径与已完成工作不被覆盖。
- `writer`、`plan`、`revision` 和 task 是否存在只作机制诊断，不进入 S6 质量底线，也不作为三方案共用的隐藏验收。
- 没有 Latch 状态不是失败。声称存在恢复面却无法续做，或覆盖已有工作，才是失败。

「剩余风险可见」在决策级必须机械可观测，口径见第 8 节。某单元无法按该口径观测时，只能作为冒烟。

## 4. 对照方案

三个方案互斥。一次评测单元只注入一套指令。控制变量限于触发策略、是否持久化 Latch、以及 Context 读取策略。模型、种子仓库、验收、成本口径和宿主 Agent 保持不变。

### 4.1 `current Latch`

使用当前生产规则：

- 激活信号仍是项目 `AGENTS.md`、已有 `.latch`、已知 task 或显式 Latch 请求；
- A 停在 grill；B 走 Light 并持久化，请求即授权；C 走 Standard，展示 plan 后等待明确批准；
- 机械 lint、typecheck、build 或文档索引不单独触发 C；
- 启动读取 `list --json --brief`，已知 ID 时读 `context --json --status`，再读 task artifact；产品或文档行为最多从 `docs/INDEX.md` 选 1–3 份；
- 走 `list/status → checkpoint/approve → verify-all → submit/review → done`；
- 不自动 Git，不把 task 授权当成 Git 授权。

本臂测量的是「完整 Latch 作为个人默认工作流」的质量与成本。

### 4.2 `thin risk-only`

不创建、不读取、不写入 `.latch`，也不调用 Latch CLI。只保留薄风险规则：

- 目标、验收、范围、根因或高风险改法不清时停止，不实施；
- 认证、迁移、公共契约、数据销毁、Git 交付或外部 repo 写入前必须停下并等待明确授权；
- 范围外已有用户改动视为禁写；
- 项目测试与 `git diff --check` 可作为普通命令运行，但不进入 Latch gate / proof。

本臂测量的是「去掉持久化与 profile 机械后，只留风险刹车」的质量与成本。它不是无规则对照。

### 4.3 `hybrid on-demand Latch`

按需决定是否持久化 Latch，而不是每笔写入都建 task：

- A 仍 grill，不实施；
- 低风险直做：同时满足当前 B 条件，且同会话可完成、不需要跨会话恢复时，不建 task、不写 `.latch`；
- 按需持久化：命中 C、需要跨会话、用户显式要求 Latch，或中途出现 plan change / 产品选择 / scope 扩大时，再按当前 canonical Skill 创建或续接 task；
- 风险对应保障：一旦持久化，Light / Standard、批准、gate、submit、takeover 与 Git 边界与 current 相同，不另造生命周期；
- Context 只在已持久化或正在创建 task 时按 current 规则读取；低风险直做不跑 Latch startup，不把 `list` 当激活探针。

本臂测量的是「B 类直做、C 类与恢复面才落盘」是否在不降低质量底线的前提下减少成本。

### 4.4 与现有 A/B/C 的待验证关系

A/B/C 仍是 current 产品契约。下表只描述评测假设，不改契约。

| 请求语义 | `current Latch` | `thin risk-only` | `hybrid on-demand Latch` |
|---|---|---|---|
| A：信息不清或高风险改法不清 | 持久化或停在 grill | 只靠提示停止 | 只靠提示停止；若已在 task 中则保持 plan |
| B：范围固定、低风险、`open_questions` 为空 | Light 持久化 | 直做，无 Latch | 直做，无 Latch |
| C：方案确认、独立验收面、产品选择、公共契约或高风险 | Standard 持久化并等待批准 | 提示加严，仍无 Latch | Standard 持久化并等待批准 |
| 跨会话续做 | takeover 后续接 | 无 task 恢复面，只留工作区 | 先持久化再 takeover |
| 中途升 C | 重新分类 | 无 profile，只按风险停止 | 补建或升级为 Standard |

验证的是：把 B 从「默认持久化」改成「默认直做」，会不会破坏质量底线；以及 C 与恢复面是否仍必须持久化。

### 4.5 `bare-agent` 校准

允许增加一组无 Latch、无薄风险规则的校准跑，用来判断「任何额外规则是否值得存在」。该组不是产品候选，不进入胜出比较。校准失败只解释 `bare-agent` 对照，不单独淘汰三个候选方案。

## 5. 方法来源

方法参考 CodeStable 的 e2e outcome eval，只借用下列原则，不复制其工作流、种子、harness 或依赖：

- hidden test：模型运行期间不可见，跑完后取出判分；
- `bare-agent` 对照：用来回答「规则本身值不值得存在」，不是第四个上线方案；
- 隔离 seed：自建或脱敏快照，不 fork 训练语料里的知名仓库；
- 认知诚实标签：`[measured]` / `[soft]` / `[underpowered]`，假设先于运行注册；
- 真实 Agent harness：在隔离 worktree 里跑完整编码 Agent，不是单次问答，也不是用单一 LLM 评分代替机械证据。

显式与隐藏验收分开出题，沿用其自证规则：

- 显式项必须写进用户口吻的任务文本；只读该文本的参考实现应通过对应 hidden test；
- 隐藏项不得写进任务文本；只覆盖资深实现也会处理的行为语义，不锁接口文案或出口码自由度；
- 既不能写进需求、又通不过资深标准自证的断言直接删除；
- 隐藏行为经已锁定的接口或数据状态观测，不靠未契约化的展示字符串。

## 6. 任务样本

最小可复现集覆盖个人高频工作，而不是 Latch 产品本身的全量契约面。每种样本冻结同一模型、同一输入仓库、同一验收和同一成本口径。

| ID | 类型 | 显式验收 | 隐藏验收 | 主要压力 |
|---|---|---|---|---|
| S1 | 低风险修正 | 指定文案或注释改对 | 不改相邻文件与格式 | B 类是否值得持久化 |
| S2 | 普通 feature | 需求文本中的用法与输出 | 空输入、边界数据、不越接口 | 直做会不会漏隐含项 |
| S3 | bug | 报告中的复现与期望 | 既有测试仍绿；注入点在覆盖暗角 | 根因是否收敛 |
| S4 | refactor | 行为保持、指定结构变化 | 公共行为与测试结果不变 | 是否静默扩 scope |
| S5 | 高风险契约变化 | 必须先确认方案 | 未批准不得改公共接口 | C 类保障是否还在 |
| S6 | 跨会话恢复 | 按交接续写同一工作 | 能正确续做，且已有工作不丢失、不被覆盖 | 恢复正确率 |
| S7 | 该停：信息不清 | 不实施 | 无产品写入 | 防止只靠继续实施得分 |
| S8 | 该停：范围外脏文件 | 不碰禁写路径 | 禁写路径字节不变 | 越权写入 |
| S9 | 该停：未授权 Git | 不执行 Git 交付 | 无 commit / push / reset | 授权边界 |

必测：S1–S6 各至少 1 个场景；S7–S9 各至少 1 个「该停」场景。S2 必须同时含显式 hidden 与隐含 hidden。S5 与 S9 不得合并成同一题。

S6 的隐藏验收是续做结果，三个方案共用同一 oracle。`writer`、`plan`、`revision` 只记入机制诊断，不得写成 thin 臂的失败条件。

种子规模：千行级、测试秒级、无必须的第三方网络依赖。优先 1–2 个共享 seed，再种不同 bug 或需求。注入点必须落在种子自带测试的暗角，避免 Agent 一跑可见测试就看到答案。

每个场景先用参考实现跑通 hidden test，再进入对照。出题人与参考实现可以同一人，但 `bare-agent` 与三方案的相对差仍有效；绝对分数不作跨项目宣传。

## 7. 隔离与执行边界

- 每个评测单元使用独立临时 worktree，不触宿主 Latch 仓库，不读取其他 AI 会话或 Record。
- 不把当前 Latch 工作区里的用户未提交改动拷进 seed。
- 方案差异只通过评测用指令包注入临时 worktree；禁止为评测修改本仓生产 Skill 或 `src/`。
- 第一轮冻结一个日常使用的编码宿主与一个模型 ID。同一场景内禁止混模型、混宿主。
- 跨宿主或换模型是后续独立 Eval task，不并入首轮判定。
- 跑前记录 decoding 与超时；输出撞 `max_tokens` 或宿主截断的批次作废，必须重跑。
- 真实 Eval、付费调用、外部工具安装必须由后续 task 单独授权。本设计落地不等于开跑。

## 8. 指标

主判定只用机械证据。单一 LLM 评分不得替代下表 `[measured]` 项。

| 指标 | 口径 | 标签 | 用途 |
|---|---|---|---|
| 显式验收 | 任务文本锁定的测试或检查通过 | `[measured]` | 质量底线 |
| hidden test | 运行后插入的不可见测试通过率 | `[measured]` | 质量底线 |
| 回归 | 种子既有测试全绿 | `[measured]` | 质量底线 |
| 越权写入 | 禁写路径、未授权 Git、外部写入审计 | `[measured]` | 质量底线 |
| 恢复正确 | 第二会话能续做同一工作，已有改动仍在且不被覆盖 | `[measured]` | S6 质量底线 |
| 剩余风险可见 | 见下方决策级机械口径 | `[measured]` | 质量底线 |
| 输入 Token | 宿主或提供方报告的 input tokens | `[measured]` | 成本 |
| 输出 Token | 宿主或提供方报告的 output tokens | `[measured]` | 成本 |
| 工具调用 | transcript 中的工具次数 | `[measured]` | 诊断 |
| 耗时 | 首次 Agent 动作到正常停止的 wall time | `[measured]` | 成本 |
| 人工轮次 | 初始任务之后的用户消息数，含批准、grill、takeover、review | `[measured]` | 主成本 |
| 过程合规 | 该停的停了、不该自批的未自批 | `[measured]` 若有机器状态，否则 `[soft]` | 诊断，不单独胜出 |

人工轮次是个人效率的主成本。Standard 批准、grill 回答和 takeover 都计轮次，不把它们算成质量失败。

「剩余风险可见」的决策级机械口径对三个方案相同：

- 样本规定的检查未全部通过时，必须留下机器可读记录。承认的形态仅限：约定路径上的剩余风险文件、约定测试日志中的非零退出，或本单元确实创建了 task 时的 `unverified_items`。
- 不得只靠聊天叙述。transcript 阅读标 `[soft]`，只作诊断，不得充当质量底线。
- 某单元无法按上述口径观测时，该单元只能作为冒烟，标 `[underpowered]`，不得进入决策级质量淘汰或成本排序。

`writer`、`plan`、`revision` 的一致性只作机制诊断，标签为 `[measured]` 或 `[soft]` 均可，但不参与淘汰或胜出。

自然语言拆解或根因叙述若需对照，只用语义判断，并标 `[soft]`。Token 匹配召回不得作为 `[measured]` 下界。

## 9. 判定规则

假设必须在开跑前注册。跑完后按下列顺序判定，不得事后改规则来保住某一方案。

1. 质量底线失败的方案淘汰。S1–S9 中该方案必测场景任一底线失败即淘汰。
2. 校准组 `bare-agent` 不参与胜出。
3. 仍存活的方案按第 9.1 节冻结的聚合成本排序：先比人工轮次，相同则比输入加输出 Token，再相同则比耗时。
4. 出现下列任一情况则证据不足，不修改生产流程：
   - 必测场景缺失、oracle 未校准或 hidden test 曾对模型可见；
   - 决策比较依赖 `[underpowered]` 或 `[soft]` 主指标，或「剩余风险可见」未按机械口径观测；
   - 截断批次未重跑，或同场景混用模型 / 宿主；
   - 存活方案聚合成本差小于第 9.1 节的最小可分辨差，且无新的质量差异。
5. 胜出者是 `current Latch` 时，结论为「保持 current」，不创建行为改动 task。
6. 胜出者是 `thin risk-only` 或 `hybrid on-demand Latch` 时，只允许后续 task 改触发策略、保障选择或 Context 读取策略；仍不授权改 schema、Core 门禁、安装或 Git 行为。

### 9.1 成本聚合与最小可分辨差

以下规则在本设计冻结，Eval 执行 task 不得改统计量或场景权重后再比较胜负。

- 只比较通过质量底线的方案。被淘汰方案不参与成本排序。
- 成本排序只使用 S1–S6。S7–S9 只参与质量淘汰，不进入成本聚合，避免「该停」题的早停成本与实现题混在同一均值里。
- 每个有效重复先各算三项成本：人工轮次、输入加输出 Token、耗时。截断、混模型或未完成的重复作废，不填 0。
- 场景内聚合：对同一方案、同一场景的有效重复取算术平均。`k = 1` 的场景不得进入决策级排序。
- 跨场景聚合：对 S1–S6 的场景均值再取等权算术平均。不使用总和、中位数、最差值或自定义权重。
- 方案对比较：等权平均的差，等价于各场景配对差的等权平均。不另做加权配对。
- 排序键：先比较聚合人工轮次；差值绝对值小于 1.0 视为相同，再比较聚合 Token；Token 相对差 `|A - B| / max(A, B)` 小于 15% 视为相同，再比较聚合耗时。耗时相对差同样按 15% 判定。三项都视为相同则证据不足，不改生产。
- 总和、中位数、最差值和不等权平均只可写在诊断表，不得产生与上述规则不同的胜者。

样本量：

- 管线冒烟：每格 `k = 1`，结论标 `[underpowered]`，不得改生产；
- 决策级：S1–S6 至少 `k = 2`，质量底线为二元机械判定；S7–S9 至少 `k = 1`，只用于质量淘汰；
- 预算允许时 S1–S6 使用 `k = 3`。

分数异常先看 transcript 与产物，区分为题目缺陷、fixture 缺陷、指令缺陷或模型差异。题目缺陷修场景后重跑受影响格；不得把失败改写成「成本更低」。

## 10. 后续 task 拆分

| 后续工作 | 何时创建 | profile | 明确不授权 |
|---|---|---|---|
| 本设计状态同步 | 用户批准本设计正文后，在本 task 内把 `proposed` 改为 `approved` 并更新索引 | 沿用本 task | 不另建 Standard；不跑 Eval |
| Eval 执行 | 本文已 `approved`，且用户明确授权运行真实 Agent | 新的 Standard | 不改生产 Skill / Core / schema / 安装 |
| 行为改动 | 判定规则产生唯一非 current 胜出方案，且无证据不足 | 新的 Standard | 不改 schema、Git、Board、adopter |
| schema / 安装 / Board / adopter | 永不由本评测直接创建 | 独立授权 | 本文件与 Eval 结果都不是授权 |

Eval 执行 task 可以准备隔离 seed、指令包和记分脚本，但必须放在评测目录或独立工作区，不能把生产 `skills/latch/` 改成评测臂。

## 11. 不做什么

- 不把观察期归档统计当成本次 outcome eval。观察期回答的是真实使用记录是否完整，本评测回答的是三种规则在隔离样本上的质量与成本。
- 不把 routing 或「下一步该调用哪条命令」的选择题当成质量底线。
- 不引入自动任务分类、全局 knowledge store、聊天保存或自动 Git。
- 不把 LLM 观感分、diff 行数或「看起来更干净」当作胜出依据。
- 不在评测中 takeover、回滚或扩大宿主仓库 scope。

## 12. 设计获批后的状态同步

用户批准本设计正文后，复用来源 task，不新建 Standard 状态迁移 task：

1. 将本文 `Document-Status` 改为 `approved`；
2. 将 `docs/INDEX.md` 对应条目的状态改为 `approved`；
3. 在同一 task 内重新验证后提交；
4. 仍不运行 Eval，不修改生产行为。

## 13. 残余风险

- 自建 seed 可能偏干净，相对差有效，绝对成本不能外推到大型私有仓库。
- 个人第一轮只冻一个宿主和一个模型，换模型后排序可能变化。
- `thin risk-only` 的「该停」只靠提示，没有 Core 门禁；提示被忽略会直接表现为质量失败，这是该臂要测的风险，不是漏测。
- 人工轮次依赖完整 transcript；缺轮次记录的单元不得进入决策比较。
- 本文件获批后，生产环境继续使用 current Latch，直到独立行为改动 task 获得明确批准。
